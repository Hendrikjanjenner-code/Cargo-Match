---
name: Demo isolation tradeoff
description: Why the expanded server demo remains separate from real identities and preserves matching parity.
---

Keep demo identity, storage, authorization and external-service access separate from real authenticated application state, even when a real session already exists.

**Why:** The shared-ecosystem request explicitly supersedes both browser-only state and private visitor exercise environments. Independent demo sessions must interact with the same business objects, but this does not authorize production impersonation or access to real customers, credentials or providers.

**How to apply:** Reuse pure domain calculations where safe, never production data services or OIDC identities. Do not import old private demo data automatically into shared tables. Persona switching changes only that session's server authority and must invalidate stale client context without discarding shared exercises. Global demo reset must warn that it affects every persona and remain separately authorized.

Compact demo forms may omit advanced management screens, but must not replace missing technical requirements with optimistic compatibility.

**Why:** A generic capacity-and-date demonstration can appear functional while teaching incorrect deepsea, breakbulk or road eligibility. The exercise is intended to explain the real product's decisions, not merely produce matches.

**How to apply:** Use explicit fictional technical examples, preserve supported requirements when editing compact forms, and compare each mode against the real pure matcher. Keep database, authentication and network dependencies out of shared matching modules.
