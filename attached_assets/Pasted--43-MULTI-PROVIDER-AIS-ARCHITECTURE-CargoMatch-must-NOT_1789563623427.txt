# 43. MULTI-PROVIDER AIS ARCHITECTURE

CargoMatch must NOT be tightly coupled to one AIS data provider.

Design the AIS architecture from the beginning to support multiple independent providers.

Initial providers to prepare for:

* VesselFinder
* MarineTraffic

Potential future providers must be addable without changing CargoMatch's core marketplace, matching, vessel, skipper or availability logic.

The purpose is to avoid vendor lock-in and allow CargoMatch to select providers based on:

* inland-waterway coverage
* geographic coverage
* data freshness
* data quality
* API availability
* commercial licensing
* cost
* available datasets

---

# 44. SEPARATE API CONNECTORS

Implement separate provider connectors.

Conceptually:

AISProvider interface

├── VesselFinderConnector

├── MarineTrafficConnector

└── FutureAISProviderConnector

Do NOT put VesselFinder-specific or MarineTraffic-specific API response structures directly into CargoMatch business logic.

Each connector is responsible for:

authentication

API requests

provider-specific parameters

pagination where applicable

rate-limit handling

provider errors

response parsing

data normalization

provider-specific identifiers

usage/cost metadata where available

# 47. VESSELFINDER CONNECTOR

Create:

VesselFinderConnector

The connector should be architecturally capable of supporting, where available under the selected commercial API plan:

* vessel position
* AIS telemetry
* vessels in geographic area
* fleet/list monitoring
* voyage information
* port calls
* vessel master data
* expected arrivals where relevant

Do NOT assume CargoMatch has access to every VesselFinder endpoint.

Feature availability must depend on configured API access.

Keep credentials in secure environment variables.

Never expose VesselFinder API keys to frontend clients.

---

# 48. MARINETRAFFIC CONNECTOR

Create:

MarineTrafficConnector

The connector should be architecturally capable of supporting available licensed MarineTraffic AIS services such as:

* vessel position
* vessel tracking
* voyage information where available
* port/vessel events where available
* vessel information where available

Do NOT assume every MarineTraffic product or endpoint is included in the account.

The connector must gracefully handle unavailable capabilities.

Keep credentials in secure environment variables.

Never expose MarineTraffic API keys to frontend clients.

# 52. FALLBACK STRATEGY

If the primary provider:

* fails
* times out
* returns no vessel
* returns stale information
* does not support the requested capability

CargoMatch may attempt the secondary provider.

Conceptually:

request telemetry

↓

PRIMARY provider

↓

valid + fresh?

YES → use result

NO

↓

SECONDARY provider

↓

valid + fresh?

YES → use result

NO

↓

AIS status unavailable

The marketplace must continue functioning when AIS is unavailable.

AIS failure must NEVER break manual commercial availability or matching.

---

# 53. DO NOT QUERY BOTH PROVIDERS BY DEFAULT

Do NOT automatically call both VesselFinder and MarineTraffic for every vessel update.

This may create unnecessary:

* API cost
* rate-limit usage
* latency
* duplicate data

Default strategy:

PRIMARY → FALLBACK

Only query multiple providers simultaneously when there is a defined business reason.

# 58. AIS DATA PROVENANCE

For every AIS-derived value, preserve enough provenance to determine:

which provider supplied it

when it was observed

when CargoMatch received it

which external vessel identifier was used

Do not lose source information during normalization.

---

# 59. PROVIDER-SPECIFIC RAW DATA

Do not spread raw provider JSON throughout the application.

If raw responses must be retained for debugging:

store them separately

apply retention limits

restrict access

respect provider licensing

never expose them directly to normal CargoMatch users

The normalized model remains authoritative for CargoMatch application logic.

---

# 60. AIS COST CONTROL

AIS data can become a significant operating cost.

Build cost-awareness into the architecture.

Avoid unnecessary polling.

Potential strategies:

higher update frequency for active participating vessels

lower frequency for inactive vessels

event-driven refresh when possible

cache recent telemetry

do not repeatedly request unchanged data

prioritize vessels with active capacity or expected availability

Track:

provider

request type

timestamp

success/failure

estimated usage units where available

This allows CargoMatch to understand AIS operating cost.

---

# 61. SMART REFRESH STRATEGY

Do not poll every participating vessel at the same frequency forever.

Example future strategy:

VESSEL WITH ACTIVE MATCH:

higher refresh priority

VESSEL APPROACHING EXPECTED AVAILABILITY:

higher refresh priority

VESSEL WITH NO ACTIVE COMMERCIAL CONTEXT:

lower refresh priority

INACTIVE VESSEL:

minimal/no refresh

The goal is commercial usefulness, not maximum tracking frequency.

# FINAL MULTI-PROVIDER PRINCIPLE

VesselFinder and MarineTraffic are DATA SOURCES.

They are not CargoMatch's business logic.

CargoMatch owns:

vessel identity mapping

commercial availability

privacy

eligibility

matching

user permissions

skipper workflow

planner workflow

commercial introductions

AIS providers only supply permitted external vessel observations.

This separation is mandatory because CargoMatch must remain operational and maintainable if:

a provider changes pricing

a provider changes API structure

coverage differs by region

one provider has an outage

a license changes

a better AIS provider becomes available

or CargoMatch later operates its own AIS data source.
