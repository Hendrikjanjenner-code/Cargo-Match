# Build CargoMatch – B2B Logistics Capacity Matching Platform

Build a production-quality MVP web application called **CargoMatch**.

CargoMatch is a B2B logistics platform that matches available or partially available inland shipping capacity with cargo that needs transportation.

The initial market is **inland shipping in the Netherlands, Belgium and the Rhine corridor into Germany**.

The core problem:

Transport companies, charterers and shipping agents often know only the available vessels inside their own network. As a result, a vessel may travel empty for a significant distance to collect cargo while another suitable empty vessel is already much closer to the loading location but is invisible because it belongs to another network.

CargoMatch should make this capacity discoverable while protecting commercially sensitive information.

The product should feel like a professional European logistics SaaS platform — not a generic marketplace.

---

# 1. Core product concept

There are two primary marketplace objects:

1. AVAILABLE CAPACITY
2. AVAILABLE CARGO

A transport company can publish that a vessel will become empty or partially empty.

Example:

Vessel type: Motor cargo vessel
Region: Antwerp
Available from: 18 September 2026 08:00
Total capacity: 1,850 tonnes
Available capacity: 1,300 tonnes
Cargo compatibility: dry bulk
Preferred direction: Rotterdam / Rhine / Germany
Maximum positioning distance: 100 km

A charterer or shipper can publish cargo.

Example:

Cargo: Grain
Weight: 1,200 tonnes
Loading location: Dordrecht
Loading window: 18 September 12:00–18:00
Destination: Duisburg
Required vessel type: dry cargo vessel

CargoMatch should automatically calculate suitable matches.

Example result:

96% MATCH

Available capacity: 1,300 t
Cargo: 1,200 t
Positioning distance: 75 km
Timing: compatible
Vessel type: compatible
Direction: compatible

# 10. Privacy model

This is extremely important.

CargoMatch should NOT immediately expose vessel identity or company identity to every marketplace participant.

Before mutual interest, other companies should see anonymized capacity.

Example:

Dry cargo vessel

Region: Antwerp
Capacity: 1,000–1,500 tonnes
Available: tomorrow from 08:00
Direction: Rhine

Button:

SHOW INTEREST

Do not show:

Exact vessel name
Exact company
Exact berth/location
Contact person
Phone number

When one party shows interest, notify the other party.

The other party can:

Accept
Decline

Only after mutual acceptance should CargoMatch reveal:

Company name
Vessel name
Contact person
Phone/email
More precise location

Create the data model and permission logic for this.

A user should never be able to bypass the UI and retrieve hidden commercial information through an API endpoint.

Enforce permissions server-side.

# 11. Matching engine

Create an explainable rule-based matching engine.

Do NOT use AI for the first matching implementation.

Start with these weights:

Distance to loading location: 30%
Timing compatibility: 25%
Capacity compatibility: 20%
Vessel type: 10%
Direction compatibility: 10%
Cargo compatibility: 5%

Total = 100%.

Every match should receive a score from 0–100.

Example:

Distance: 95/100
Timing: 100/100
Capacity: 98/100
Vessel type: 100/100
Direction: 85/100
Cargo compatibility: 100/100

Overall:

96% MATCH

Store both the total score and component scores.

Create an explanation such as:

"Excellent match because the vessel becomes available before the loading window, has sufficient capacity and is located close to the loading location."

Do not claim exact travel time unless routing data supports it.

For MVP geographic calculations, calculate approximate positioning distance based on coordinates.

Structure the matching service so that real inland-waterway routing can replace this later.

# 14. Private Networks

This is a core differentiator.

Create three visibility/matching levels:

Company's own fleet and directly managed vessels.

LEVEL 2 — TRUSTED PARTNERS

LEVEL 3 — OPEN CARGOMATCH NETWORK

All eligible marketplace participants.

When cargo is created, show matches grouped by these levels.

Example:

No suitable vessel within 75 km.

TRUSTED PARTNERS

1 vessel
87% match

OPEN CARGOMATCH NETWORK

4 vessels

Allow a company to choose visibility when publishing capacity:

Enforce these visibility settings in backend queries and APIs.

SHOW INTEREST

ACCEPT

Both companies can communicate.

# 28. Development approach

Before writing large amounts of code:

1. Review this specification.
2. Create a concise implementation plan.
3. Define the database schema.
4. Define routes/pages.
5. Define authorization rules.
6. Define matching-engine functions.
7. Then build the application incrementally.

Do not replace core functionality with static mockups.

Where an external API is unavailable, create a clean fallback implementation.

Run the application after major changes.

Fix TypeScript errors, runtime errors and broken routes before continuing.

Use reusable components.

Keep business logic separate from presentation logic.

Add comments only where they genuinely help explain non-obvious business logic.

---

# 29. MVP acceptance criteria

The project is ready for pilot testing when:

* A user can register and create a company.
* A carrier can create vessels.
* A carrier can publish available capacity.
* A charterer can publish cargo.
* Locations can be selected and stored with coordinates.
* Cargo and capacity appear on the map.
* The matching engine automatically creates matches.
* Matches have explainable component scores.
* Users can filter and view matches.
* Commercial information remains anonymized before mutual acceptance.
* Users can show interest.
* The counterparty can accept or decline.
* Identity/contact details are revealed only after acceptance.
* A conversation is created after acceptance.
* Private-network visibility works.
* Notifications work.
* The dashboard displays real database data.
* Demo data can be loaded.
* The application works on desktop and mobile.
* There are no major TypeScript/runtime errors.
* Sensitive authorization is enforced server-side.
