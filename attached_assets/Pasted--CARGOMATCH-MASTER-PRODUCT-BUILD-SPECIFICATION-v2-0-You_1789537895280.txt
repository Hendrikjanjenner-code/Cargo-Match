# CARGOMATCH — MASTER PRODUCT & BUILD SPECIFICATION v2.0

You are the lead product engineer and software architect responsible for building **CargoMatch**, a professional B2B logistics capacity-matching platform.

Treat this document as the authoritative product specification.

Do not blindly build everything at once.

First understand the business rules, architecture, privacy model, data model, matching logic and state machines. Then build the product incrementally, starting with the core end-to-end vertical slice.

When requirements conflict, prioritize in this order:

1. Security and authorization
2. Commercial privacy
3. Correct business rules
4. Core end-to-end workflow
5. Data integrity
6. Matching correctness
7. User experience
8. Secondary functionality
9. Visual polish

---

# 1. PRODUCT

Product name:

**CargoMatch**

CargoMatch is a B2B logistics platform that matches available or partially available transport capacity with cargo that needs transportation.

The first version focuses exclusively on:

**European inland shipping**

Initial geography:

* Netherlands
* Belgium
* Rhine corridor into Western Germany

Do NOT build trucks, rail or containers as separate transport modes in the MVP.

The architecture may prepare for them later.

---

# 2. PROBLEM

Transport companies, charterers, agents and shippers frequently operate inside their own commercial networks.

A charterer may know 50 suitable vessels.

Another company may know another 100 vessels.

These networks do not necessarily overlap.

As a result, a vessel may travel empty for a significant distance to collect cargo while another suitable vessel is already much closer to the loading location.

The closer vessel may be invisible because:

* it belongs to another commercial network
* its future availability is unknown
* it is partially loaded but has spare capacity
* its operator does not know about the cargo
* the cargo owner does not know about the vessel

CargoMatch should make these opportunities discoverable without requiring companies to publicly expose commercially sensitive information.

---

# 3. CORE VALUE PROPOSITION

CargoMatch should answer:

> "What suitable transport capacity is available near this cargo?"

and:

> "What suitable cargo is available near where my vessel becomes available?"

The system should create privacy-protected commercial introductions.

CargoMatch MVP is NOT a freight booking platform.

CargoMatch does NOT:

* negotiate prices
* create freight contracts
* reserve vessel capacity
* confirm transport bookings
* guarantee vessel suitability
* guarantee navigability
* calculate exact sailing routes
* claim verified cost savings
* claim verified CO2 savings

The MVP facilitates discovery, matching, consent-based identity disclosure and communication.

---

# 4. CORE PILOT HYPOTHESIS

Every product decision should support testing this hypothesis:

> "Will logistics companies share privacy-protected available capacity, and will CargoMatch create commercially useful introductions between cargo and nearby suitable capacity?"

When choosing between adding functionality and making the core workflow more reliable, always prioritize the core workflow.

# 7. MULTI-TENANT ARCHITECTURE

# 18. ELIGIBILITY ENGINE

Eligibility MUST happen before scoring.

Create a separate module:

EligibilityEngine

Conceptually:

isEligible(cargo, capacityOffer)

Return:

eligible: true/false

and machine-readable reasons.

Exclude a pair if:

* cargo is not ACTIVE
* capacity offer is not ACTIVE
* either listing is expired
* either company is suspended
* visibility rules prevent discovery
* capacity is insufficient
* vessel type is incompatible
* cargo compatibility is incompatible
* availability cannot satisfy loading requirements
* maximum approximate positioning distance is exceeded
* required data is missing

Only eligible pairs proceed to scoring.

# 73. MVP ACCEPTANCE TEST

The MVP is pilot-ready only when this exact scenario succeeds:

1. User A registers.

2. User A creates Carrier Company A.

3. User A creates Vessel A.

4. User A publishes 1,300 tonnes available capacity near Antwerp.

5. User B registers.

6. User B creates Charterer Company B.

7. User B publishes 1,200 tonnes cargo from Dordrecht to Duisburg.

8. Eligibility engine confirms compatibility.

9. Matching engine calculates score.

10. Both parties receive privacy-safe match representations.

11. Neither party can retrieve unauthorized identity/private details through direct API calls.

12. User B clicks SHOW INTEREST.

13. User A receives notification.

14. User A clicks ACCEPT.

15. Match becomes CONNECTED.

16. Authorized identity/contact information becomes available.

17. Exactly one conversation is created.

18. Both parties can exchange messages.

19. Unrelated Company C cannot retrieve match-private information or messages.

20. CONNECTED is not displayed as booked transport.

If this journey fails, the MVP is not complete.
